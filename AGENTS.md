# AGENTS.md

## Project state

Early-stage Drogon plugin library for OpenAI-compatible APIs: OpenAI itself, or any endpoint that speaks the same format, such as DeepSeek. It is consumed by other Drogon apps (e.g. `../assistantbot`). The typed API covers Chat Completions (creation, parsing, streaming and stored completion management); unwrapped JSON/binary/multipart methods, pages, and polling cover custom paths. The remaining 23 root API groups are implemented against the pinned openai-python 3.41.0 catalog (57 resource classes, 146 HTTP methods), including Responses helpers, upload polling, webhook verification and WebSocket sessions. Only authentication/deployment extensions in TODO.md are deferred; admin.*, deprecated Assistants and other beta.* remain excluded.

- The library target is `drogon-openai` (alias `drogon-openai::drogon-openai`). It is static by default; pass `-DBUILD_SHARED_LIBS=ON` for a shared build.
- Public headers live in `include/drogon_openai/` and are installed through the `HEADERS` file set. Consumers include `<drogon_openai/...>`. Private headers go in `src/`, which is only on the library's own include path.
- The plugin class is `drogon_openai::OpenAIClient` (`drogon::Plugin<OpenAIClient>`). Apps register it by class name under `plugins` in their config.json. Drogon calls `initAndStart(config)` inside `app().run()`, before beginning advices, so `app().getPlugin<drogon_openai::OpenAIClient>()` only works after `run()` starts.
- Registration relies on drogon's static `DrObject<T>::alloc_` initializer. With the static library, the linker only pulls in `openai_client.o` when the app references the class. If the app lists the plugin in config.json but never calls `getPlugin<OpenAIClient>()` (or otherwise uses the class), drogon logs `Plugin drogon_openai::OpenAIClient undefined!` and keeps running without it.
- Plugin config keys: `max_retries` (default 2), `timeout` (scalar seconds or connect/read/write object; defaults 5/600/600), `default_headers`, `default_query`, `organization`, and `project` are optional. Negative retries and non-finite/negative timeouts are rejected. `base_url` and `model` are required, and `initAndStart` throws `std::invalid_argument` if either is empty. The API key is never read from config.json. The optional `api_key_env` names the environment variable that holds it, and `initAndStart` throws if that variable is unset or empty. Without `api_key_env`, `api_key` stays empty (endpoints without auth). The optional `webhook_secret_env` likewise reads a non-empty webhook signing secret from an environment variable; omit it or leave the name empty when unused. Add new keys to `OpenAIConfig`, `initAndStart`, the class doc comment, `config.json`, and the tables in `docs/*/drogon-plugin.md`.
- The client API mirrors the OpenAI Python SDK's `AsyncOpenAI`: `OpenAIClient::NewOpenAIClient()` returns an `OpenAI` client by value, and `co_await client.chat.completions.Create(ChatCompletionCreateParams)` yields `Result<ChatCompletion>` (`std::expected<T, Error>`, in `error.hpp`). `Create` returns `drogon::Task<...>`. There is no sync API, because drogon's docs advise against sync calls on event loops. `OpenAI` is a value handle: `chat` and `completions` are plain members, and the only shared state is one `std::shared_ptr<details::Transport>`. Copies are cheap and share the transport, so pass an `OpenAI` client to coroutines by value. Don't wrap API groups in pointers unless one needs polymorphism or non-copyable state. Request and response structs live in `types/chat.hpp`, named after `openai.types.chat`. The API groups (`details::Chat`, `details::Completions`) share one `details::Transport` (private, `src/details/`), which applies defaults, auth, request overrides, asynchronous retries and error metadata. `src/details/http_exchange.*` implements incremental HTTP/1.1 framing on Trantor TCP/TLS; `src/details/chat_json.*` serializes and decodes chat JSON; `src/details/chat_stream.*` frames SSE and accumulates stream events. Add new request fields to the params struct, to `to_request_body` in `src/details/chat_json.cpp`, to the parameter tables in `docs/*/drogon-plugin.md`, and to the full wire fixture in `tests/test_chat_json.cpp` (retain the existing `CreateSendsSetOptionalFields` checks too).
- Coroutines take their parameters by value (drogon's coroutine guidance), and `Completions::Create` copies `m_transport` into its frame before the first `co_await`. Keep both rules in new API methods.
- Every request attempt owns a fresh Trantor TCP/TLS client on the caller's event loop (main loop for threads without one). This preserves concurrency and continuation-thread affinity. DNS callbacks are marshalled onto that loop. Never cache a connection or block an event loop with `sync_wait`.
- Streaming is incremental, including HTTP chunked, Content-Length and EOF framing, SSE line fragmentation/UTF-8/multiline data, indexed parallel function/custom tools, text/refusal/reasoning/logprobs events, cancellation and final usage. `Stream` returns the accumulated completion, equivalent to Python's `get_final_completion`. Started streams never retry; missing `[DONE]` fails validation. Callback exceptions map to `InvalidRequest`.
- The transport validates TLS certificate chains and hostnames with system roots and requests identity content encoding. It currently has no redirects, decompression, proxy settings, HTTP/2 or pooling. Trantor 1.5.28's `TcpConnectionImpl::sendInLoop` / `writeCallback` do not reliably invoke the installed write-complete callback. Request `sendStream` EOF switches from write to read deadlines after the socket/TLS layer accepts the bytes; `bytesSent()` progress bounds write inactivity. Keep the phase regression tests.
- SDK behavior was checked against openai-python 3.41.0 (`src/openai/_base_client.py`, `_constants.py`, `types/chat/`, and `lib/streaming/chat/`). Defaults: two retries, connect 5/read 600/write 600 seconds; retry connection/timeouts, 408/409/429/>=500, with jittered 0.5–8 second backoff and response-header overrides. Finite Retry-After >120 seconds suppresses retries. OPENAI_LOG info/debug logs only method/host/attempt/delay.
- `WithOptions`/`Copy` merge headers case-insensitively and query keys; per-request overrides win. `CreateRaw`/`RequestRaw` expose metadata; typed responses retain `raw` and `_request_id`. Error metadata includes type/code/param/request_id/headers and HTTP status predicates.
- `Parse` takes an explicit response JSON Schema, rejects non-strict/non-function tools before sending, decodes structured content and strict arguments, and fails length/content_filter finish reasons. Providers enforce schemas; optional `schema_validator` integrates a complete caller-supplied validator. The library does not generate schemas or implement partial JSON Schema validation.
- `Page<T>` owns its continuation; `GetNextPage`, `ForEach`, and `All` preserve request settings and detect repeated cursors. `OpenAI::List(..., cursor=false)` represents an SDK-style single page. `Poll` supports configurable terminal states and honors `openai-poll-after-ms`; its absolute deadline includes all request phases, retries and delays. `PostAndPoll`/`UploadAndPoll` poll the collection/id path using the returned string ID; their deadline starts after creation. Typed polling helpers cover Files, Videos and Vector Stores; PollRaw retains terminal HTTP metadata.

- Non-chat resources use `types/<group>.hpp`, `details/<group>.hpp` and `src/details/resource_<group>.cpp`. `details/text_completions.hpp` is the legacy text API; never overwrite `details/completions.hpp`, which is Chat Completions. Nested SDK models/unions remain Json::Value; primitives are typed and unknown response fields stay in raw. ResourcePayload separates query parameters from body, including GET extra_body and POST query fields. Multipart uses SDK bracket notation, with explicit SDP/JSON parts for Realtime calls.
- Resource generation reads the pinned SDK AST without importing or executing it. See tools/README.md, tools/sdk_resources.json and tools/resource_extensions.json. Regenerate bindings, contract tests and mirrored docs together. Helpers in resource_helpers.cpp, resource_connections.cpp and resource_webhook_signatures.cpp are handwritten. Normal builds need no Python. Generated checks cover all endpoints; independent test_resource_wire, test_resource_helpers and test_websocket must still validate protocol behavior.
- Page<T> supports normal last-item cursors and explicit last_id for Conversations, Videos and checkpoint permissions. SDK single-page APIs such as vector search do not continue. Preserve owned continuation settings and advance after even when the original extra_query contained after.
- WebSocketSession shares one connection across copies. It owns frame bytes, bounds unread data to 16 MiB, allows only one pending receive, and marshals completion to each awaiter's loop. Receive(timeout=0) has no deadline; a receive timeout leaves the session usable. Send success means queued bytes. Close and release sessions before stopping drogon. Drogon 1.9.13 discards non-101 WebSocket handshake responses, so rejection is Connection without HTTP metadata; there is no automatic reconnect/replay.
- Webhook verification uses OpenSSL::Crypto HMAC-SHA256, constant-time comparison, the original payload bytes and a default 300-second replay window; invalid signatures use ErrorKind::InvalidWebhookSignature. CMake and the installed package find OpenSSL Crypto explicitly (provided by Drogon's vcpkg dependencies).

## Consuming the library

The library supports two ways to consume it. Keep both working when you change `CMakeLists.txt`.

- From source: `add_subdirectory(<path>)`, or CPM with `SOURCE_DIR`/`GIT_REPOSITORY`. `PROJECT_IS_TOP_LEVEL` is false then, so `DROGON_OPENAI_BUILD_TESTS` and `DROGON_OPENAI_INSTALL` default to OFF. Neither the tests nor `enable_testing()` reach the consumer, and nothing is installed into the consumer's prefix.
- Installed: `just publish` installs into `publish/` (`lib/`, `include/`, `lib/cmake/drogon-openai/`). Consumers set `CMAKE_PREFIX_PATH` to that directory and call `find_package(drogon-openai CONFIG REQUIRED)`. The package config calls `find_dependency(Drogon CONFIG)` and `find_dependency(OpenSSL COMPONENTS Crypto)`, so consumers don't need their own `find_package(Drogon)`. Version compatibility is `SameMinorVersion`. The install tree includes the reference SDK Apache license under `share/licenses/drogon-openai/`.
  - The GitHub Release packages (`drogon-openai-<version>-<os>-x64`, see the Release workflow below) are the same install tree plus `LICENSE`, from the release build only. Consumers still get drogon from vcpkg, with `x64-windows-static-md` on Windows.
- Either way, link `drogon-openai::drogon-openai`. It carries `Drogon::Drogon` publicly.

## Tests

The tests use drogon's own framework, `drogon/drogon_test.h`, which is installed with drogon, so the tests add no dependency. They follow `../drogon-onebot`'s setup.

- `tests/CMakeLists.txt` globs `tests/test_*.cpp` (non-recursive, `CONFIGURE_DEPENDS`) and builds each file into its own executable named after the file stem (`build/<preset>/tests/test_chat_completions`). Each one links `drogon-openai::drogon-openai`, has a private include path to `src/` for protocol/serialization unit tests, and gets `cxx_std_23` (for `<print>`). Adding a `tests/test_*.cpp` file is enough. Removing one leaves its old binary until `just clean`.
- Each executable is registered with CTest:
  - `WORKING_DIRECTORY` is the repo root (for `config.json`), and `TIMEOUT` is 60.
  - `RESOURCE_LOCK config_json_listener` serializes them under `ctest -j`, because the app-backed tests share the listener port.
  - `SKIP_RETURN_CODE 77` reports a test as skipped.
  - A block after the loop gives `test_deepseek` the `live` label and `TIMEOUT 300`. It names the test, so renaming the file means updating that block.
- The executables take drogon's test options: `-r <name>` runs one `DROGON_TEST`, `-s` prints passing checks, and `-l` lists the tests.
- `tests/support.hpp` holds the shared helpers:
  - `run_tests_with_app` follows drogon's `lib/tests/main_CookieSameSite.cc`. It runs `app().run()` on a background thread and waits for a beginning advice plus `LISTEN_DELAY`, because listeners start after the advices. Then it runs the tests on the main thread and quits the app.
  - `drogon::test::run()` answers `-l` and `-h` by calling `exit()` (`drogon_test.cc:171`, `:205`). With the app thread running, the process then dies with a trantor `FATAL` and exit code 1, so `run_tests_with_app` passes those options straight to `drogon::test::run()` without starting the app (`prints_and_exits`). `../drogon-onebot`'s copy does not do this yet.
  - The test thread runs no event loop, so tests may block on `drogon::sync_wait` (`Create`) or `HttpClient::sendRequest`. `sendRequestCoro` returns an awaiter, not an awaitable, so `sync_wait` rejects it.
- `config.json` (tracked, no secrets) is the shared fixture:
  - It listens on `127.0.0.1:18081` (`../drogon-onebot` uses 18080, so both suites can run at once). `base_url` is `http://127.0.0.1:18081/v1`, so the plugin's client exercises the path prefix.
  - `model` is `fake-model`, and `api_key_env` is `DROGON_OPENAI_TEST_API_KEY`. The tests set that variable themselves.
  - `document_root` is `/tmp/drogon-openai-example`. Drogon creates `uploads/tmp/00` to `FF` under it on startup (`HttpAppFrameworkImpl.cc:535`), so every test that runs the app loads `config.json`, `test_deepseek` included, to keep those directories out of the repo.

Calls `initAndStart` on test-built plugins without running the app: the required `base_url` and `model` (missing or empty), `api_key_env` (read, unset, empty), and the tracked `config.json`. |

- `test_resources` covers the 146 generated HTTP bindings; `test_resource_wire` independently checks JSON/query/body/multipart/binary/text/cursors and errors. `test_resource_helpers` covers Responses parsing/SSE, bounded upload concurrency, ordered upload parts and a Python-derived HMAC vector. `test_websocket` covers six connection routes, loop affinity, frame ownership, receive exclusivity, deadlines and closing. These use local fixtures without OpenAI credentials.

- The fake endpoints in `test_chat_completions` record each request in `g_last_request` on the IO thread before answering, so a test reads its own request after `sync_wait` returns. Path prefixes select the fake's behavior (`/minimal`, `/unauthorized`, `/slow`, ...), and each successful endpoint uses its own completion `id`, so a test can tell which one answered.
- `ConcurrentRequestsDoNotQueue` sends two requests to `/slow` (1 s each) from two threads and requires them to finish within 1.8 s. `CreateResumesOnCallingThread` calls `Create` from a coroutine handler on the IO thread and compares `std::this_thread::get_id()` before and after the `co_await`. Each fails when the transport shares one client, or always uses the main loop, respectively.
- `CreateUnreachableIsConnectionError` connects to `127.0.0.1:1` with a 10 s timeout. Windows retries a refused connect for about 2 s before it reports the failure, so a timeout of 2 s or less yields `Timeout` there instead of `Connection`. On Linux the connect fails immediately.
- `ctest --preset linux-debug -LE live` runs only the offline tests.

## Commands

`just` drives the build. Recipes map onto CMake presets named `<os>-<profile>` (`linux-debug`, `linux-release`, `windows-debug`, `windows-release`), with build trees in `build/<preset>/`.

- `just init`: run `vcpkg install` for the packages in `vcpkg_deps` (currently `drogon`), in classic mode (no `vcpkg.json`; `VCPKG_ROOT` must be set). On Windows it passes `--triplet x64-windows-static-md --host-triplet x64-windows-static-md`, so the dependencies are static libraries linked against the dynamic CRT, and the `windows-base` preset sets `VCPKG_TARGET_TRIPLET` to the same triplet so `find_package` looks in that installed tree. Keep the two in sync: the vcpkg toolchain ignores `VCPKG_DEFAULT_TRIPLET` and would fall back to `x64-windows`. Other platforms use vcpkg's default triplet.
- `just build [debug|release]`: configure only if `build/<preset>/CMakeCache.txt` is missing, then build, then copy `compile_commands.json` to `build/`. A cache left by a failed configure makes this skip configure and fail with `loading 'build.ninja'`; fix it with `just configure debug --fresh`.
- `just test [profile]`: build, then `ctest --preset <os>-<profile>` (output on failure; no tests is an error). It runs `test_deepseek` too when `DEEPSEEK_API_KEY` is set.
- `just run <target> [profile]`: build everything, then run `build/<os>-<profile>/tests/<target>`, e.g. `just run test_chat_completions` or `just run test_config release`. `<target>` is required.
- `just publish [profile]`: build (default `release`) and `cmake --install` into `publish/`.
- `just clean [profile]`: delete `build/<os>-<profile>/`, or `build/` and `publish/` when no profile is given.
- `just docs`: create `build/doxygen` (Doxygen does not create the output path) and run `doxygen Doxyfile`; open `build/doxygen/html/index.html`.
- Without just: `cmake --workflow --preset linux-debug` configures, builds, and tests.

## CI, version tags, and docs

`linux-ci.yml`, `version-tag.yml`, and `docs.yml` started as copies of `../drogon-onebot`'s, which follow `yizhinailong/mcr` (pinned action SHAs with the version in a comment, checksum-verified tool downloads, logic inline in the YAML). `windows-ci.yml` and `release.yml`, the `workflow_call` trigger and package steps in `linux-ci.yml`, and the Release dispatch in `version-tag.yml` follow mcr's workflows of the same names. Keep the shared parts in step with `../drogon-onebot` when changing them. `docs/*/ci.md` and `docs/*/doxygen.md` describe the workflows for users; keep those pages in sync.

- `.github/workflows/linux-ci.yml` (Linux CI) runs on every branch push, PR, and manual dispatch, and as a reusable workflow (`workflow_call`) from Release on version tags. Its `push` trigger covers branches only, so a tag runs it only through Release. It runs a `debug` and a `release` matrix leg on `ubuntu-24.04`.
  - Tools: CMake 4.2.3 (Kitware tarball, SHA-256 pinned) and LLVM 21 from apt.llvm.org (signing key fingerprint checked). `/usr/lib/llvm-21/bin` goes on `PATH`, so the presets' plain `clang++` resolves to LLVM 21.
  - Steps: `clang-format --dry-run -Werror` (debug leg only), then `vcpkg install drogon`, then `cmake --preset`, `cmake --build --preset`, and `ctest --preset`.
  - CI sets no `DEEPSEEK_API_KEY`, so `test_deepseek` reports skipped and CI never calls DeepSeek.
  - vcpkg is a shallow fetch of the pinned commit `67972e92`, the checkout that provides drogon 1.9.13 port-version 2, the version these docs cite. Bump `VCPKG_COMMIT` (in both CI workflows) only after verifying locally on the same commit.
  - The vcpkg binary cache is restored and saved with `actions/cache/restore` and `actions/cache/save` right after the install, so a failing build still keeps the dependencies. The key includes `ImageOS`, the vcpkg commit, `gcc -dumpfullversion` (vcpkg builds the ports with the system GCC), and the CMake version.
  - On a tag, a step after configure compares the tag with `CMAKE_PROJECT_VERSION` from `CMakeCache.txt`. CMake parses that value itself, which double-checks the tag workflow's text parsing.
  - On a tag, the `release` leg runs `cmake --install` into `$RUNNER_TEMP/drogon-openai-<version>-linux-x64/`, adds `LICENSE`, packs it as `.tar.gz`, and uploads it as the `drogon-openai-linux-x64` artifact (7 days).
  - The ubuntu-24.04 image has GCC 12 to 14. Clang 21 uses the newest libstdc++ it finds (14).
- `.github/workflows/windows-ci.yml` (Windows CI) has the same triggers, matrix, tag check, and packaging as Linux CI, on `windows-2025` with `shell: pwsh`. It does not check formatting; the Linux debug leg does.
  - `ilammy/msvc-dev-cmd` sets up the x64 MSVC environment first, which `clang-cl` needs. The CMake 4.2.3 zip and ccache 4.14.2 (the presets hard-wire ccache, and the image has none), both SHA-256 pinned, go on `GITHUB_PATH` after it, so they come before Visual Studio's CMake 3.31. LLVM (`clang-cl`) and Ninja come from the image, which had LLVM 20.1.8 and Ninja 1.13.2 as of image 20261021; the install step prints them.
  - vcpkg uses the same commit, `bootstrap-vcpkg.bat`, and `--triplet`/`--host-triplet` from `VCPKG_TRIPLET` (`x64-windows-static-md`, the same as `just init` and the `windows-base` preset). vcpkg builds the ports with MSVC and its own CMake, so the cache key is `ImageOS`, the triplet, the vcpkg commit, and `VCToolsVersion`.
  - GitHub's pwsh wrapper only checks the last exit code, so `run:` scripts with several native commands set `$PSNativeCommandUseErrorActionPreference = $true`. Don't pipe a native command into `Select-Object -First` there, because stopping it early can count as a failure; index the captured output instead.
  - On a tag, the `release` leg packs `drogon-openai-<version>-windows-x64.zip` with `Compress-Archive` and uploads it as the `drogon-openai-windows-x64` artifact.
- `.github/workflows/release.yml` (Release) runs on pushed `v*` tags and on manual dispatch. It calls both CI workflows with `uses:`, then its publish job (tags only, after both pass; the only job with `contents: write`) downloads the `drogon-openai-*` artifacts and runs `gh release create --verify-tag --generate-notes` with the title `drogon-openai <VERSION>`, or `gh release upload --clobber` when the release already exists. Runs for one tag queue instead of cancelling each other.
  - The packages hold the release build only, by decision. On Windows that library uses `/MD`, so consumers' Debug builds (`/MDd`) cannot link it (`LNK2038`) and build from source instead.
- `.github/workflows/version-tag.yml` runs on pushes to `master` that touch `CMakeLists.txt`, and on manual dispatch.
  - It reads `VERSION` from the first `project()` call at the push's before and after commits. It strips `#` line comments, and the value must be a literal `major[.minor[.patch[.tweak]]]`. On a change, it creates the annotated tag `v<VERSION>` (`drogon-openai <VERSION>`) on the pushed commit.
  - A before commit without a usable version is only a baseline. A tag that already points at another commit fails the run; one on the same commit is reused.
  - Tags pushed with `GITHUB_TOKEN` do not trigger push workflows, so it then runs `gh workflow run release.yml --ref <tag>`. That is why Release keeps `workflow_dispatch`.
- `.github/workflows/docs.yml` builds the Doxygen site with Doxygen 1.18.0 (SHA-256 pinned) on pushes to `master` that touch the documented paths, then deploys it to GitHub Pages. Pages must use the "GitHub Actions" source in the repository settings.
  - It appends `WARN_AS_ERROR = FAIL_ON_WARNINGS` through stdin (`( cat Doxyfile; echo ... ) | doxygen -`), so any comment warning fails the run.
  - The `Doxyfile` itself keeps `NO`, because older local Doxygen versions warn about unknown 1.18 tags.
- Check workflow edits with `actionlint` (with `shellcheck` on `PATH`, so the bash `run:` scripts are checked too). actionlint does not check the pwsh scripts of Windows CI; run changed pwsh steps locally with the `GITHUB_*` files pointed at a temp directory.

## Build notes

- Requires CMake >= 4.0, Ninja, and ccache (hard-wired as `CMAKE_CXX_COMPILER_LAUNCHER`). Compiler is `clang++` on Linux, `clang-cl` on Windows.
- The UCRT deprecates `getenv`, and clang-cl warns about every call. Read environment variables with `read_env` in `src/openai_client.cpp` or `test_support::get_env` in the tests. Both use `_dupenv_s` on Windows and `getenv` elsewhere.
- Don't set `CMAKE_CXX_STANDARD` here. The library declares `target_compile_features(PUBLIC cxx_std_23)` (the public headers use `std::expected`), which is exported to `find_package` consumers. A parent project's `CMAKE_CXX_STANDARD` still applies in `add_subdirectory` mode, so under a C++26 parent the library builds with `-std=gnu++26`. The test executables add `cxx_std_23` for `<print>`.
- Drogon 1.9.13's `FindFilesystem.cmake` (run by `find_package(Drogon)`) leaves an unset `CMAKE_CXX_STANDARD` defined as `""`, and `target_compile_features` then fails with `CXX_STANDARD property ... contained an invalid value: ""`. Both `CMakeLists.txt` and `cmake/drogon-openai-config.cmake.in` unset the empty value right after finding Drogon. Keep those blocks.
- Sources and public headers are collected with `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)`, so adding a file triggers a re-configure on the next build.

## Code style

New C++ code follows the `cpp-style-ref` skill (CMake + vcpkg variant), the same as `../assistantbot`: types and public methods PascalCase, private members `m_`, namespaces lowercase, `/** @file ... @brief ... */` at the top of every file, Doxygen blocks repeated on out-of-line definitions, `T const&`, brace initialization, and trailing return types. Drogon's virtual overrides (`initAndStart`, `shutdown`) keep their upstream names.

Format with `clang-format -i <files>` (root `.clang-format`, same as `../assistantbot`). Check with `clang-format --dry-run -Werror <files>`.

`.clang-format` sets `LineEnding: LF`, so the dry run flags every line of a CRLF file. `.gitattributes` (`* text=auto eol=lf`) overrides `core.autocrlf` and checks every file out with LF, Windows included. A working tree from before `.gitattributes` keeps its CRLF files until they are converted or checked out again.
